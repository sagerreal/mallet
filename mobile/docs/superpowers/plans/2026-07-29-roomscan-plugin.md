# MalletRoomScan Capacitor plugin (phase 2B) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The native half of the scan bridge: a Capacitor plugin in the existing shell (`com.trymallet.app`) that presents the RoomPlan capture screen full-screen and returns the captured geometry to the web app — so tapping "Scan room" in Mallet on Owen's iPhone scans a room and lands a room card.

**Architecture:** `shell/ios/App/App/RoomScanPlugin.swift` (CAPPlugin) + `RoomScanViewController.swift` (RoomCaptureView host) linking the existing `MalletCapture` SPM package (local path dep). Registration via a `CAPBridgeViewController` subclass's `capacitorDidLoad` + `bridge?.registerPluginInstance(...)` — the documented trap: `packageClassList` is minted by `cap sync` from npm packages only; hand-editing it gets wiped, and dropping a .swift file registers nothing.

**Contract (must match `lib/native/room-scan.ts` in mallet-app's feat/scan-bridge — the web side is the source of truth):**
`captureRoom({ roomName: string })` resolves `{ status: "done", rawPayload: string, geometry: string, capturedAt: string }` (JSON strings: rawPayload = verbatim CapturedRoom JSON; geometry = NormalizedGeometry snake_case wire via the package's toWire path; capturedAt ISO-8601) or `{ status: "cancelled" }`; rejects on hard errors (deviceNotSupported, capture failure).

## Global Constraints

- The shell repo rules (mallet-ios README): npm not pnpm in shell/; SPM not CocoaPods; `cap sync` overwrites `ios/App/App/public` + the generated capacitor.config.json — never hand-edit those; Info.plist already carries NSCameraUsageDescription.
- MalletCapture package: add as a local SPM dependency of the App target (path `../../../capture/MalletCapture` — verify the relative depth from App.xcodeproj). Use MalletCaptureCore + MalletCaptureRoomPlan products.
- All Apple-type mapping stays in the framework (RoomPlanExtractor / SurfaceMapper) — the plugin only orchestrates: run session → CapturedRoom → `RoomPlanExtractor.surfaces` → `SurfaceMapper.geometry` → wire JSON. NO new geometry math in the shell.
- Coaching: surface `CaptureCoaching` guidance strings as the in-scan hint label (the four states); RoomCaptureView's own overlay stays on too.
- Device gating: no LiDAR / iOS < 17 → the plugin's `available()` method returns `{ available: false, reason }` and `captureRoom` rejects with the same reason. (The web side hides the button when the plugin object is absent; on a non-Pro iPhone the plugin EXISTS but must report unavailable — the web's roomScanPlugin() gate alone is not enough. Flag this to the web branch if its gating needs `available()` — check feat/scan-bridge's lib/native/room-scan.ts and reconcile: preferred reconciliation is the web calls available() once and hides the button on false.)
- Crash-safety: persist via the framework's CaptureStore BEFORE resolving to the web (the phone may lose the webview mid-return); the store is the native-side backup — the web ingest is the system of record once it succeeds.
- Explicit user-controlled Done/Cancel; portrait; the sheet look consistent with the app (launch-cream background, no dead chrome).
- Verification on this machine is compile-only (`xcodebuild ... -destination 'id=350BF3A6-686B-569D-A3D2-663D3670390F' build` for the connected iPhone, CODE_SIGNING via team 6SMLK52FUJ already baked). RoomPlan cannot run in any simulator — the live test is Owen's.
